# Shared method for the maker projects

This repository is one of four independent projects: plant monitoring, rain alerts for hanging laundry, an exit reminder, and an availability light. Cross-project decisions will be recorded in the repositories they affect, with links between related issues or decision records. The initial specifications are proposals for review; they do not describe built devices or verified integrations.

## Working method

We will keep specifications current: define expected behavior and acceptance criteria first, then design, architecture, and technology decisions, followed by small tasks, prototypes, and evidence. A behavior change updates the specification in the same repository as the implementation.

Each README orients the reader. The `specs/` directory holds verifiable behavior. Future technical decisions belong in `docs/decisions/`. We will add code, CAD, and electronics directories when they contain useful artifacts.

Spec Kit may help organize this process. We will initialize it in each repository after there is a local checkout and we have confirmed the structure generated by the installed version. These files do not mean Spec Kit has already been installed.

## Language and localization

Repository documentation, specifications, code identifiers, and source UI copy will be written in English. The intended product languages are English and Spanish. For a JavaScript or TypeScript user interface, use Lingui to extract, maintain, and compile message catalogs once the application exists. Set English as the source locale and provide a Spanish catalog. Keep user-visible strings translatable, including normal, alert, unknown, and error states. Verify both languages in the actual interface, including text length and accessibility labels. This is a product direction, not a claim that Lingui has been installed in any repository.

A small device without a JavaScript or TypeScript UI may need a different localization mechanism. Share stable state and event meanings across devices; do not make Spanish or English display text the machine-to-machine contract. Lingui references: [React tutorial](https://lingui.dev/tutorials/react/) and [CLI](https://lingui.dev/ref/cli).

## Proposed cross-project architecture

Each physical object should handle its main use case on its own. When a central display is useful, the project will send events through a shared contract that still needs definition. The display will decide how to present priority, age, and unknown states; it will not take over sensor rules. Local Wi-Fi is a candidate for automatic alerts. NFC may support deliberate close-range interactions. Transport, event format, and security will be decided with an initial integration prototype.

## Shared next steps

1. Validate each project's main behavior with a physical test.
2. Choose sensors, power, enclosure, and placement based on that test.
3. Define an alert contract only for projects that need it.
4. Record decisions and test results in each repository.
